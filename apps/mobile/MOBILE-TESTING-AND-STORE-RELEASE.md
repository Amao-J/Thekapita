# Mobile testing and store release guide

This guide covers local development, device testing, and publishing theKapita's Expo app to Google Play and Apple's App Store. Commands are written for Windows PowerShell, and should be run from the indicated directory.

## Project-specific facts to check first

- The mobile app is an Expo SDK 57 / React Native app in the `apps/mobile` workspace. The npm lockfile is at the repository root.
- The Expo app configuration already sets the Android package and iOS bundle identifier to `com.thekapita.app`, and the display version to `0.1.0`. Confirm you control this identifier and want to keep it before creating store records; changing it after publishing means creating a different app.
- `apps/mobile/app.json` sets `extra.apiBaseUrl` to `https://api.thekapita.com/api`. Mobile test builds will therefore call the production API unless that configuration is deliberately changed. Prefer a staging API with test accounts and test data. Do not test payments or other write actions with real users, accounts, or funds.
- The app uses `react-native-bottom-tabs`, a native dependency. Expo Go does not include every third-party native module, so it may not run this app correctly. Use a **development build** for dependable testing.
- There is no `apps/mobile/eas.json` or configured app icon in the current project snapshot. EAS build configuration and store-ready artwork still need to be prepared.
- This computer is Windows. Android can be built locally with Android Studio; iOS cloud builds can be created with EAS, but running an iOS Simulator or using Xcode locally requires macOS.

## 1. Install dependencies and check the project

Install the monorepo dependencies from the repository root (the directory containing the root `package.json` and `package-lock.json`):

```powershell
npm ci
```

Then check the Expo app configuration and dependency compatibility:

```powershell
Set-Location apps\mobile
npx expo-doctor
npx expo install --check
```

Resolve any compatibility/configuration errors before building. The app currently has no dedicated automated mobile test script, so these checks do not replace manually exercising the app on devices.

### Optional quick preview with Expo Go

Expo Go is useful for a fast first look if the installed Expo Go version supports this project's SDK and native modules:

```powershell
Set-Location <repository-root>
npm run start --workspace @thekapita/mobile
```

Install Expo Go on a phone and scan the QR code. Both devices should normally be on the same network. If the screen reports a missing native module or cannot load the app, switch to a development build below; do not treat an Expo Go failure as a release-build test.

## 2. Recommended: test with a development build

A development build includes the app's native dependencies and connects to Metro for fast JavaScript updates.

### One-time setup

From the mobile app directory:

```powershell
Set-Location apps\mobile
npx expo install expo-dev-client
npx eas-cli@latest build:configure
```

The second command creates EAS project/build configuration (including `eas.json`) and may ask you to log in or link an Expo project. Create an Expo account at [expo.dev](https://expo.dev/) if needed, then authenticate with:

```powershell
npx eas-cli@latest login
npx eas-cli@latest whoami
```

The EAS configuration belongs in `apps/mobile`, not at the monorepo root. The normal profiles are:

- `development`: development client, for app coding and device QA.
- `preview`: internal, production-like build for stakeholder testing.
- `production`: store-signed build.

If configuring `eas.json` manually, a good starting point is:

```json
{
  "cli": {
    "appVersionSource": "remote"
  },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal"
    },
    "preview": {
      "distribution": "internal",
      "android": {
        "buildType": "apk"
      }
    },
    "production": {
      "autoIncrement": true
    }
  }
}
```

Keep any configuration generated by `eas build:configure` that is needed for your project; merge settings rather than replacing it blindly. The Android preview APK is for direct testing, not Play Store submission.

### Build and install on Android

For local builds, install Android Studio, the Android SDK, and an emulator, or connect a physical Android device with USB debugging enabled. From `apps/mobile`:

```powershell
npx expo run:android
```

This generates native Android project files if needed, builds, installs, and starts the app. You can also build a development APK in EAS cloud, which is convenient if Android Studio is not installed:

```powershell
npx eas-cli@latest build --platform android --profile development
```

Install the completed build using the EAS build page's installation link or follow its device instructions.

### Build and install on iOS

For an iOS Simulator, use a separate EAS development profile with `ios.simulator` set to `true`, then build it in the cloud. The simulator binary can only be run on a Mac with the iOS Simulator.

For a physical iPhone, create an iOS development build:

```powershell
npx eas-cli@latest build --platform ios --profile development
```

EAS will guide you through Apple signing and device registration. Installing directly on iPhones generally requires Apple Developer signing/provisioning. EAS cloud builds work from Windows; local Xcode/iOS Simulator builds do not.

### Start the app during development

Once the development build is installed, start Metro from `apps/mobile`:

```powershell
npx expo start --dev-client
```

Open the installed theKapita development app and connect to the displayed development server. Keep the phone and computer on the same Wi-Fi network; if the network/firewall prevents a LAN connection, try:

```powershell
npx expo start --dev-client --tunnel
```

JavaScript and screen changes normally appear through Fast Refresh without rebuilding the native app. Rebuild after adding/updating a native library or changing native app configuration such as `app.json`.

## 3. Manual mobile smoke-test checklist

Use a staging backend and test account where possible. Test on at least one physical Android device and one physical iPhone before release.

1. **First launch and authentication**
   - Fresh install opens the landing screen for a signed-out user.
   - Get started opens sign-in; sign-in and registration show useful errors for invalid input or unavailable network.
   - Successful authentication reaches the signed-in destination.
   - Force-close and reopen: a valid session is restored; sign-out returns to the unauthenticated experience.
2. **Navigation and device behavior**
   - Visit each available tab and return to the landing/home destination.
   - Check Android system Back, iOS safe areas/notches, keyboard interactions, scrolling, and small-screen layouts.
   - Exercise foreground/background and resume, rotate only if orientation support is intended, and verify no blank screen or crash.
3. **Backend-dependent screens**
   - Test wallet balance/history and other account data using designated test accounts.
   - Test food and ride flows only as far as the staging setup safely permits; confirm loading, empty, error, and success states.
   - Verify network loss, slow responses, expired sessions, and API errors do not silently appear as successful transactions.
4. **Release-like installation**
   - Install a preview build on a clean device and test without Metro.
   - Check permissions, app name/icon, links, and that API requests use the intended staging/production environment.
   - Verify an upgrade over the previous version preserves expected account/session behavior.

## 4. Prepare store accounts and app metadata

Before creating release builds:

1. Create an app entry in [Google Play Console](https://play.google.com/console/) and [App Store Connect](https://appstoreconnect.apple.com/). Ensure both use the intended `com.thekapita.app` identifier.
2. Enroll in the relevant developer programs. Google Play requires a Play Developer account; Apple requires Apple Developer Program membership for App Store releases.
3. Add a production app icon and any launch/splash artwork to Expo app configuration. Prepare store screenshots, descriptions, support contact, age/content ratings, and release notes.
4. Publish a privacy policy and accurately complete each store's privacy/data-safety disclosures. The app has account, wallet, ride, and food functionality: disclose actual data collection/sharing, permissions, and retention rather than relying on assumptions. Provide any account deletion and reviewer test-account details required by the stores.
5. Separate staging and production API settings. Confirm the production endpoint, TLS, logging, operational monitoring, and test-account access are ready. Never put passwords, API keys, or signing credentials in the app bundle or source control.
6. Confirm versioning. The current user-facing version is `0.1.0`. The suggested EAS configuration uses remote auto-increment for store build numbers so repeat uploads do not reuse an Android `versionCode` or iOS `buildNumber`.

Google Play registration may require a one-time fee; Apple Developer Program membership is paid and typically renewed annually. Confirm current terms and pricing on the official store sites.

## 5. Build signed store binaries

EAS Build is the recommended option for this Windows workstation: Android and iOS are built in the cloud, so a Mac is not required to create the iOS archive. Run EAS commands from the mobile app directory:

```powershell
Set-Location apps\mobile
npx eas-cli@latest build --platform all --profile production
```

Or build each platform separately:

```powershell
npx eas-cli@latest build --platform android --profile production
npx eas-cli@latest build --platform ios --profile production
```

Expected store artifacts:

- Android: signed `.aab` (the recommended Google Play upload format).
- iOS: signed `.ipa` for App Store Connect/TestFlight.

On the first build, EAS may ask to create/manage signing credentials. Android keystore and Apple distribution credentials are sensitive: let EAS securely manage them or store your own securely, and keep recovery access restricted. Do not commit credentials to Git or paste them into chat.

Track builds and open the EAS build details page:

```powershell
npx eas-cli@latest build:list --limit 5
```

## 6. Submit and release

### Google Play

1. Configure an Android Google Play service-account key in EAS credentials for submission. Keep the downloaded JSON key out of the repository.
2. Upload the first build to Play Console's **Internal testing** track and install it through the tester opt-in link.
3. Review crashes, account flows, payments, permissions, and store disclosures with the internal group before promoting to closed/open testing or production.
4. Submit the latest production build through EAS:

```powershell
npx eas-cli@latest submit --platform android --latest
```

For the first app release, follow Play Console's app setup and release prompts; Expo Submit uploads the bundle but does not complete the listing, content declarations, screenshots, or review.

### Apple App Store

1. Create the app record in App Store Connect with the matching bundle identifier. Configure Apple signing credentials in EAS when prompted.
2. Upload to TestFlight:

```powershell
npx eas-cli@latest submit --platform ios --latest
```

3. Wait for App Store Connect processing, then test with internal TestFlight users. Complete the app listing, privacy details, screenshots, export-compliance questions, and review information.
4. Select the tested build and submit it for App Review in App Store Connect. Uploading to TestFlight does **not** release the app publicly.

Store submissions can also be performed manually from the Play Console and App Store Connect. EAS Submit is recommended for uploads, but store metadata, screenshots, policy declarations, review, and rollout are still managed in the store consoles.

## Recommendation

Use **EAS development builds** for day-to-day phone testing, **EAS preview builds** for stakeholder acceptance, and **EAS production builds plus internal testing/TestFlight** before public release. Because this project includes native bottom tabs and the current API configuration points at production, do not rely on Expo Go or use real accounts/transactions as test data. First establish a staging API and complete the icon, privacy, and store-listing work; then build and test Android and iOS through EAS from Windows.
